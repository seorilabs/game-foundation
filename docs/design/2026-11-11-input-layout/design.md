# E2E 입력 도우미의 배치 안정 판정

- 상태: 계약 1.3.0에 포함([진행 초기화와 베타 공용 수정 반영](../2026-11-28-progress-reset/design.md)). 처음 고친 곳은 betta-raising v0.1.3 검수(2026-11-11, 로컬 브랜치)이고, 2026-11-28에 원본으로 옮겼다.
- 범위: 테스트 도우미 `godot/tests/common/e2e_driver.gd`와 검사 `godot/tests/common/input_layout_probe.gd`만 바꾼다. 제품 규칙, 화면, SDK는 바꾸지 않는다.

## 원래 실패

betta-raising 공동 수조 검수에서 568×320 지원코드 복사 단계의 `scroll_into_view`가 한 번 false를 돌려줬다. 근본 원인은 확정하지 못했다. 같은 조건을 재현하는 component 검사로 두 가지 잘못된 판정을 확인했다.

1. 끌기 도중 스크롤 컨테이너가 커져 스크롤 위치는 그대로인데 대상이 보이게 되어도 false를 돌려줬다.
2. 화면 크기가 바뀌는 중에 스크롤 위치만 2프레임 같으면 안정됐다고 보고 판정했다.

## 고친 판정

- 끌기 뒤에는 화면, 스크롤 범위, 대상 사각형, 스크롤 위치가 함께 4번 같은 값일 때까지 기다린다(`_settle`). 그 뒤 스크롤 위치가 같아도 실제 보임 조건으로 다시 판정한다.
- 계속 가려진 대상은 실패한다. 대상이 끝없이 움직여(유휴 맥동 등) 안정 대기가 시간 초과로 끝나면 그때의 보임 조건으로 판정한다(2026-11-28 로컬 리뷰 반영).
- 보임 계산의 오차, 실제 좌표 입력, 임계값은 바꾸지 않았다.
- 검수 장면을 내린 뒤 오디오 자원이 해제될 때까지 200ms 실제 시간을 기다린다(`unmount`). 빠른 headless 실행에서 다음 fixture가 이전 장면의 재생 자원과 겹치지 않게 한다.

## 검증

`input_layout_probe`가 위 1, 2와 끝없이 움직이는 대상을 재현하고, 수정 전 코드에서 실패하는 것을 확인했다. 실제 UI 여정 대신 끌기를 직접 제어하는 component 검사라 여정 수에는 넣지 않는다.
